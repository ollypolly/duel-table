# Duel Table — Plan

A local web tool for visualising Yu-Gi-Oh! games: a board you can step through, where every card shows its art and text, driven by scripted scenarios that Claude writes. The owner is new to Yu-Gi-Oh, so the point is **learning**: watch a combo or a matchup play out step by step with narration, pause, rewind, fork from any step and try something different.

This is **Level 1** of a bigger idea. Level 1 includes a small **local HTTP API**, so Claude (via `curl`) or any script can drive a live board, not just author files. An MCP server is Level 2 and should fall out of that API almost for free. See [Future: Level 2](#future-level-2-mcp-on-top-of-the-api).

## Scope

**In (Level 1):**
- Render a two-player board with all zones, and a card detail panel (art + full text + stats).
- Load scenarios (JSON) made of steps. Each step applies board actions and shows narration.
- Step forward/back, play/pause, scrub, keyboard shortcuts.
- Fork: from any step, switch into free-play, move cards by hand, and save the result as a new branch (persisted locally, exportable as scenario JSON).
- Local card database + images, fetched once from YGOPRODeck.
- A localhost API server that owns **live sessions** (a board in progress). The browser shows a session live and updates as actions arrive, whether they come from the owner clicking or from Claude calling the API.

**Out:**
- **No rules implemented.** The tool tracks where cards are, like a real table. It doesn't enforce legality, resolve chains automatically or run card effects; rules live in the narration. Full rules automation is what EDOPro/YGO Omega spend years on. **But the architecture must leave room for it.** See [Designed for rules later](#designed-for-rules-later): build the seams now, not the rules.
- No hosted backend, accounts or real multiplayer. The API binds to `127.0.0.1` only.
- Pendulum zones, Link arrows and Rush/Speed Duel formats. Ignore them unless trivial.

## Stack

- **Vite + React + TypeScript** (strict). Scaffold with `npm create vite@latest . -- --template react-ts` rather than hand-writing config.
- **Zustand** with the `persist` middleware (localStorage) for app/player state. Add `immer` middleware only if updates get awkward.
- **Zod** to validate scenario and deck files at load, with good error messages (Claude will author these, so bad files must fail loudly and clearly).
- **Tailwind CSS v4** via the official Vite plugin.
- **Motion** (`motion/react`) for card movement between zones via shared `layoutId`. Nice to have, not phase 1.
- **react-markdown** for narration.
- **Vitest** (+ Testing Library for a few component tests).
- `tsx` to run the Node scripts in `scripts/` and the API server in dev.
- **Hono** (`@hono/node-server`) for the API, with **`@hono/zod-openapi`** so routes are defined from the same Zod schemas the engine uses and an OpenAPI spec is generated. That spec is what the Level 2 MCP tools get derived from.
- **Server-Sent Events** for pushing session updates to the browser (one-way push is all we need; actions go in via normal POSTs).
- `concurrently` so `npm run dev` starts Vite and the API together. Vite proxies `/api` to the server.

Before wiring Zustand persist, Tailwind v4, Motion or Hono/zod-openapi, check current docs via the context7 MCP; APIs have moved recently. Use npm unless there's a reason not to (pnpm is also installed).

## Architecture

```
duel-table/
  scripts/
    fetch-cards.ts        # builds the local card DB + downloads images
  data/
    cards.json            # generated subset of the card DB (committed)
  decks/
    chazz-armed-ojama.json
  scenarios/
    ojama-vs-super-quant-t1-t3.json
  sessions/               # live sessions saved as JSON (gitignored)
  public/
    cards/                # downloaded images (gitignored, regenerated by script)
  server/                 # Node only. Imports src/engine, src/scenarios/schema, src/data
    index.ts              # Hono app, binds 127.0.0.1
    routes/               # scenarios, sessions, cards
    sessions.ts           # session service: create, apply, undo, fork, export (transport-agnostic)
    events.ts             # SSE fan-out per session
  src/
    engine/               # PURE TypeScript. No React, no DOM, no Zustand.
      types.ts            # BoardState, CardInstance, ZoneRef, Action
      actions.ts          # applyAction(state, action) -> state
      replay.ts           # stateAt(scenario, stepIndex)
      setup.ts            # scenario setup -> initial BoardState
      rng.ts              # seeded RNG + shuffle
      selectors.ts        # derived values: current ATK, current name, etc.
      zones.ts            # data-driven zone definitions
      rules/              # RulesProvider interface + tableRules
      cards/              # CardScript types + (empty) registry
    data/
      cardDb.ts           # load cards.json, lookup by passcode / name
    scenarios/
      schema.ts           # Zod schemas for scenario + deck files (pure, shared with server)
      resolve.ts          # validate + resolve names -> passcodes (pure, shared with server)
      load.ts             # browser-only: import.meta.glob over scenarios/ -> resolve.ts
    api/
      client.ts           # typed fetch client + SSE subscription for live sessions
    store/
      playerStore.ts      # current scenario, step index, playing, speed (persisted)
      branchStore.ts      # user-made branches (persisted)
      uiStore.ts          # selected card, open pile viewer (not persisted)
    components/
      Board/ Zone/ CardView/ CardDetail/ CardInspector/ Hand/ PileViewer/
      StepControls/ NarrationPanel/ ScenarioPicker/
    App.tsx
```

**Why `src/engine` stays pure:** the browser, the API server and the future MCP server all run the exact same engine and action types. So nothing in `engine/` may import React, Zustand, Node or browser APIs. The store and the server call the engine; the engine never knows about either. Same rule for `scenarios/schema.ts`, `scenarios/resolve.ts` and `data/cardDb.ts` (take the card JSON as an argument rather than fetching it).

**Layering:** `engine` (pure rules of the table) → `server/sessions.ts` (session service, no HTTP in it) → transports (`server/routes/` today, an MCP adapter in Level 2). Keep HTTP details out of the service so a second transport is a thin wrapper.

## Data model

### Cards

- `CardData`: from the local DB. `id` (passcode), `name`, `type`, `desc`, `atk`, `def`, `level`/`rank`/`linkval`, `attribute`, `race`, `archetype`, image paths.
- `CardInstance`: one physical card in a game. `iid` (unique per game, e.g. `p1-ojamatch-2`), `cardId`, `owner` (`p1` | `p2`), `faceUp`, `position` (`atk` | `def`), `materials: iid[]` (Xyz materials sit under the monster, not in a zone).
- Custom cards: scenarios may define `{ custom: { name, text, atk?, def? } }` for cards not in the DB (e.g. a placeholder for an opponent card we're unsure of). Render them with a generic frame.

### Zones

Per player: `deck`, `hand`, `extraDeck`, `gy`, `banished`, `monster[0..4]`, `spellTrap[0..4]`, `fieldSpell`. Shared: `extraMonster[0..1]`.

`ZoneRef` is e.g. `{ player: 'p1', zone: 'monster', slot: 2 }` or `{ player: 'p2', zone: 'gy' }`. Piles are ordered arrays (top of deck = index 0).

### BoardState

```ts
{
  players: { p1: PlayerState; p2: PlayerState }  // lp, name, zones
  extraMonster: [iid | null, iid | null]
  cards: Record<iid, CardInstance>
  turn: number
  activePlayer: 'p1' | 'p2'
  phase: 'draw' | 'standby' | 'main1' | 'battle' | 'main2' | 'end'
  chain: ChainLink[]                 // { card, player, label? } — manually pushed/resolved for now
  modifiers: Modifier[]              // see below
  history: HistoryEntry[]            // per-duel facts, e.g. "p1 Special Summoned Armed Dragon LV7"
  turnFlags: { normalSummonUsed: Record<Player, boolean>; oncePerTurn: Record<string, true> }
  rng: { seed: number; cursor: number }  // RNG lives in state so replay stays pure
  highlights: iid[]                  // cleared every step unless re-set
  arrows: { from: iid; to: iid }[]   // e.g. targeting, attacks; cleared every step
}
```

`Modifier` is a generic temporary change on a card: `{ id, target: iid, kind, value, source?: iid, until: 'endOfTurn' | 'endOfNextTurn' | 'permanent' | 'leavesField' }`, where `kind` is one of `atk`, `def`, `name` (Fusion Tag), `negated`, `unaffected`, `cannotAttack`, … (an open union). In Level 1 they're applied by hand via actions and the UI just displays them ("ATK halved", "treated as VW-Tiger Catapult"). That alone is great for learning, and it's exactly the shape a rules layer would need. Derived values (current ATK, current name) come from selector functions in `engine/`, never stored.

`history` and `turnFlags` are filled by the engine as a side effect of actions (e.g. every Special Summon appends an entry; `nextTurn` resets turn flags). Armed Dragon Catapult Cannon's "must have Special Summoned both materials this duel" is the motivating example.

### Actions

A discriminated union on `type`. Keep this list small and composable:

- `move` `{ card, to, faceUp?, position?, index? }`: the workhorse (summon, send to GY, banish, bounce, add to hand, set).
- `draw` `{ player, count }`
- `shuffle` `{ player, zone }`: uses the scenario's seeded RNG.
- `lp` `{ player, delta }` or `{ player, set }`
- `phase` `{ phase }` / `nextTurn`
- `attach` `{ card, to }` / `detach` `{ card, to }`: Xyz materials.
- `flip` `{ card }` / `position` `{ card, position }`
- `reveal` `{ cards }`: shows face-down/hand cards for this step only.
- `highlight` `{ cards }` / `arrow` `{ from, to }`
- `modify` `{ modifier }` / `unmodify` `{ id }`
- `chainPush` `{ card, label? }` / `chainResolve`: lets scenarios *show* a chain building and resolving in reverse, which is one of the most confusing things for a beginner.

Every action can carry an optional `cause`: `{ card?: iid, reason: 'cost' | 'effect' | 'battle' | 'rule' | 'manual' }`. It's ignored by the Level 1 reducer apart from being logged, but it's what trigger effects key off ("if this card is sent from the hand to the GY as a cost…").

Scenario authors refer to cards by **iid** after setup. Names are only used in setup (see below).

## Designed for rules later

We are not implementing rules. We are making sure adding them later is an extension, not a rewrite. The seams:

1. **Two layers of action.** *Primitive actions* (above) are physical moves; the reducer applies them. *Intents* are game-level moves: `{ type: 'activate', card, effect? }`, `normalSummon`, `specialSummon`, `attack`, `declarePhase`, … A step may carry an optional `intent` alongside its primitive `actions`. In Level 1 the intent is descriptive only (used for the step label and a badge). Later, a rules layer turns intents into primitive actions itself.
2. **Events out of the reducer.** `applyAction` returns `{ state, events }`, where events are typed facts like `movedZone { card, from, to, cause }`, `summoned { card, method }`, `lpChanged`. Level 1 only uses them for the log panel and animations. Triggers ("when this is sent to the GY…") would subscribe to these.
3. **A pluggable `RulesProvider` interface** in `engine/rules/`:
   ```ts
   interface RulesProvider {
     validate(state: BoardState, action: Action): Issue[]        // warnings/errors, never throws
     legalIntents?(state: BoardState, player: Player): Intent[]  // later: "what can I do?"
     resolveIntent?(state: BoardState, intent: Intent): Action[] // later: intent -> primitive actions
   }
   ```
   Level 1 ships one implementation, `tableRules`: physical checks only (slot occupied, card not where you said it was). The UI surfaces issues as non-blocking warnings, so free-play can do anything a real table allows. A future `basicRules` could add turn structure and summon limits; a future card-effects layer builds on that.
4. **A card script registry** (`engine/cards/registry.ts`): `Record<passcode, CardScript>`, empty in Level 1. The `CardScript` type is sketched but unused, e.g. `{ effects: EffectDef[] }` where an `EffectDef` has a condition, cost and resolution that produce primitive actions. Card data (from the API) and card behaviour (scripts) stay separate.
5. **Data-driven zones.** Zone definitions (name, capacity, ordered/unordered, public/private) live in one table, not hard-coded across components, so adding e.g. Pendulum zones is a table entry plus layout.
6. **Everything pure, serialisable and deterministic.** No `Date.now()`/`Math.random()` in the engine. Same inputs → same state, which is what makes replay, forks, tests and a future rules engine all work.

Guardrail: implement each seam at its simplest (a type, an empty registry, a trivial provider), with a test proving the seam is wired. Don't build speculative rules logic.

## Scenarios

```jsonc
{
  "id": "ojama-vs-super-quant-t1-t3",
  "title": "Armed Ojama vs Super Quant: turns 1–3",
  "description": "...",
  "seed": 42,
  "players": {
    "p1": { "name": "You", "deck": "chazz-armed-ojama" },
    "p2": { "name": "Friend", "cards": ["Super Quantum Red Layer", "..."] }
  },
  "setup": {
    // explicit starting positions; anything unplaced stays in the deck
    "p1": { "hand": ["Ojamatch", "Ojamagic", "Ojamassimilation", "Fusion Tag", "Ash Blossom & Joyous Spring"] }
  },
  "steps": [
    {
      "label": "Ojamatch",
      "narration": "Activate **Ojamatch**, sending Ojamagic as the cost...",
      "actions": [ { "type": "move", "card": "p1-ojamatch-1", "to": { "player": "p1", "zone": "spellTrap", "slot": 0 } } ]
    }
  ]
}
```

- **iids are generated deterministically at setup** from owner + slugged name + copy number (`p1-ojamatch-1`), so authors can predict them. Expose a dev-only "copy iid" on hover to make authoring easy.
- Names resolve to passcodes via the card DB at load. Unknown names are a validation error listing close matches.
- **Forks** are scenarios with `"extends": { "scenario": "<id>", "atStep": 7 }`: they replay the parent's first N steps, then continue with their own. User-made branches from free-play use the same shape, so they can be exported and dropped into `scenarios/`.
- Replay: `stateAt(scenario, n)` = reduce steps `0..n` over the setup state. Scrubbing backwards is just recomputing. Cheap at this scale; memoise if needed.

## Card data (YGOPRODeck)

API docs: https://ygoprodeck.com/api-guide/. Key rules from their terms:

- Endpoint: `https://db.ygoprodeck.com/api/v7/cardinfo.php` (`name=` pipe-separated exact names, `id=` comma-separated passcodes, `fname=` fuzzy).
- **Rate limit 20 req/s; exceeding it blocks you for an hour.** Stay well under (batch names into one request where possible).
- **Do not hotlink images.** Download and self-host them, or risk an IP blacklist. Images live at `card_images[].image_url` / `image_url_small` / `image_url_cropped`.
- `checkDBVer.php` returns the DB version; store it in `data/cards.json` and skip refetching when unchanged.

`scripts/fetch-cards.ts` (`npm run fetch-cards`):
1. Collect every card name referenced by `decks/*.json` and `scenarios/*.json`.
2. Fetch them in batches, write a trimmed `data/cards.json` (only fields we use + DB version).
3. Download full + small images to `public/cards/{id}.jpg` and `public/cards/small/{id}.jpg`, skipping existing files.
4. Report unknown names with fuzzy suggestions.

Commit `data/cards.json` (small, makes tests and fresh clones work). Gitignore `public/cards/`.

## UI

- **Board** laid out like a playmat: opponent mirrored on top, you at the bottom, LP and phase in the header. Hands at the far top/bottom (opponent hand face-down unless revealed).
- **Piles** (deck, Extra Deck, GY, banished) show a count + top card. Click to open a **PileViewer** listing the contents. Your deck/Extra Deck contents are visible in this tool (it's for learning).
- **Card detail panel**: click/hover any face-up card to see full art, name, stats and text. Keep it docked on the right on desktop.
- **Narration panel** under or beside the board: current step label + markdown narration.
- **Step controls**: first / prev / play-pause / next / last, a scrubber showing step labels, speed control. Keys: ←/→ step, space play/pause, Home/End.
- Highlights (glow) and arrows (SVG overlay) for "this card targets that one".
- **Deep links:** `?scenario=<id>&step=<n>` opens straight to that step, and the URL updates as you step. That lets Claude point the owner at an exact moment ("open this link, look at step 7").
- Scenario files hot-reload in dev (Vite HMR via `import.meta.glob`), so a scenario Claude writes or edits shows up in the open browser without a restart.
- Desktop-first. Don't break on a narrow screen, but a mobile layout isn't a goal.

### Swappable renderer (2D now, Three.js later)

The board renderer must be replaceable by a 3D one (react-three-fiber) without touching anything else:

- `src/view/boardView.ts` (pure): `BoardState` + card lookup → `BoardView`, a flat description of every zone and card (face, image, position, derived ATK/name, highlighted/revealed flags). Renderers read only this, never the engine or stores.
- `src/view/layout.ts` (pure): playmat geometry in abstract table units (each zone slot's x/y/rotation). The 2D board positions cards from it, a 3D board places meshes from it, and arrows are drawn from it rather than by measuring the DOM.
- `BoardRenderer` contract: props `{ view, events, onCardClick, onZoneClick, onCardHover }`, where `events` are the last step's engine events (for animations). `Board2D` is the Level 1 implementation.
- Panels (detail, narration, step controls, pile viewer, free-play controls) are DOM around whichever renderer is active, so they're shared.

## Local API

The API owns **sessions**. A session is a board in progress: a setup (usually "scenario X at step N"), plus the list of steps applied since. That makes a session's log the same shape as a scenario, so exporting one is trivial and a good live game can become a scenario file.

Endpoints (all JSON, all validated by Zod, all under `/api`):

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/scenarios` | List scenarios (id, title, step count) |
| GET | `/scenarios/:id` | Full resolved scenario |
| GET | `/cards?name=` / `/cards/:id` | Card lookup (text, stats, image path). Handy for Claude to check card text |
| POST | `/sessions` | Create `{ scenario?, atStep?, deck?, seed? }` → `{ id, state }` |
| GET | `/sessions` / `/sessions/:id` | List / get current state + step log |
| POST | `/sessions/:id/steps` | Apply `{ actions, intent?, narration? }` → `{ state, events, issues }` |
| POST | `/sessions/:id/undo` | Drop the last step |
| POST | `/sessions/:id/fork` | New session from this one at step N |
| POST | `/sessions/:id/export` | Write it to `scenarios/<id>.json` (or return the JSON) |
| GET | `/sessions/:id/events` | SSE stream: `state` after every change |
| GET | `/openapi.json` | Generated spec |

- `issues` come from the `RulesProvider` (`tableRules` today). They're warnings: the step still applies unless the request sets `strict: true`.
- Sessions are held in memory and written to `sessions/<id>.json` after every change, so they survive restarts and Claude can read them directly.
- Browser: a **Live** mode alongside scenario playback. Pick or create a session; the board follows its SSE stream; free-play moves the owner makes are POSTed as steps, so Claude and the owner act on the same board. Scenario playback keeps working without the server (pure client-side replay).
- Deep link for live mode: `?session=<id>`.

## Persistence

- `playerStore` (persisted): last scenario id, step index, playback speed.
- `branchStore` (persisted): user branches, stored in the fork shape above, with export-to-JSON (download) and import.
- Version the persisted schemas (Zustand persist `version` + `migrate`) from day one.

## Level 2: Claude in the app

Claude runs inside the app, as an opponent first and then as a teacher. The HTTP API stays as it is, so Claude Code can still drive sessions from outside.

### Bring your own intelligence

The app works fully without AI, and logging in to Claude adds intelligence on top. There are two tiers:

- **Without Claude:**
  - preset lessons and scenarios;
  - free play and branches;
  - games on the rules engine against the random bot.

  Everything here is authored ahead of time or is rules-only.
- **With Claude (your own login):**
  - Claude as the opponent;
  - coaching while you duel against it;
  - lessons and scenarios made on request, and interactive ones that react to what you do, instead of only the presets.

The server reports whether a Claude login is available. The UI shows the Claude features only when it is, and otherwise offers them as "log in to Claude to…". Nothing AI runs unless you're logged in. Claude features stay additive, so the free tier never depends on them.

### Decisions

- **Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk`), not the raw Messages API. It covers several things we'd otherwise build ourselves:
  - conversation persistence and resume;
  - context compaction;
  - streaming input, so viewer events can be queued while a turn is running;
  - interrupt (the Stop button);
  - per-run usage and cost.
- **Auth.** Locally, it uses the owner's Claude Code login. That's allowed for personal use only, so no API key is needed. There's no login inside the app: you run `claude` and `/login` on the machine running the server, and the server rechecks when a New game dialog opens (at most every 30s). If the app is hosted, an `ANTHROPIC_API_KEY` from env takes over, because claude.ai login can't be offered to other users. The displayed cost is the API-equivalent figure, labelled as such, since a subscription doesn't charge per call.
- **Only our tools.** Built-in Claude Code tools (Bash, file edits, web) are disabled. Our tools are an in-process MCP server (`createSdkMcpServer` with Zod tools). Each tool is a thin wrapper over `server/sessions.ts`, alongside the HTTP routes, and reuses their schemas.
- **Transport.** Existing SSE plus POST, no WebSocket. Claude's chat, status and cost are part of the game's view, so they arrive over the session SSE stream as whole messages (no token streaming). The browser sends chat, Stop, Resume and settings as POSTs.
- **Layout.** The Claude panel (chat, Stop/Resume, model, Coach, Show my cards, cost) sits in the scene panel under the game's question. Step narration stays below it.
- **Rules.** Games against Claude run on OCG Core (spiked, see below). Free play, scenarios and lessons stay on our own engine.
- **Models.** Opus by default, with Sonnet selectable, since Sonnet is quicker for an opponent's turn.

### Play against Claude (first)

OCG Core owns the rules, turn flow and hidden information. It asks each player what to do. You answer by clicking; Claude answers its own questions with tools.

**Built (server/games.ts, server/ocg/):**
- **Games are sessions.** `POST /games` picks both decks; the session's steps are translated from the core, and `duel.responses` in the session file holds every answer given. A restart rebuilds the duel by replaying them (like `.yrp` replays). Games refuse posted steps and undo (409).
- **Questions as options.** Each core prompt becomes a `GamePrompt` (`src/api/game.ts`): a message plus numbered options, each optionally tied to a card iid, with how many to pick. The answer is the list of picked indices (`POST /sessions/{id}/game/answer`). Claude's tools will use the same shape.
- **Auto-answered:** zone placement (first free zone), a single legal position or option, sorting, and chances to chain when nothing just happened (no summon, attack or activation, and an empty chain), as most clients do. A "stop at every chance" toggle may be needed for traps in the End Phase.
- **Hidden info in prompts:** labels never name the opponent's face-down or in-hand cards. The browser still receives full board state, as sessions always have; the board just doesn't show those faces. Fine locally, not for hosting.
- **Bots.** Any player can be a random bot (`bots`, default `["p2"]`), with its steps paced at 700ms. The free-tier opponent, and used in tests.
- **Browser.** "New game against the bot…" in the Live menu. The scene panel lists the options (grouped by card, with a filter for long lists and checkboxes for multi-picks); the cards involved are lit on the board, and clicking one narrows to its options or picks it.

**Built (Claude as p2, server/claude/):**
- **Turns.** When the core asks Claude's player something, or you chat, Claude gets one message: your chat, what happened since it last looked, card texts it hasn't had yet, the table, and the question. It answers with the `answer` tool, whose result carries the next question, so a whole turn is one run. Other tools: `table` and `card`. Built-in Claude Code tools are off. A question ignored twice gets the first option picked for it.
- **Fair play.** Claude never sees iids (they spell card names). The table text is written from Claude's side only, from `BoardState` plus who can see each card, and step labels blank the names of cards it can't see. A fake-agent test plays whole games and checks every message for hidden names and iids.
- **Card text.** The real text of each card goes in the first time Claude knows of it, so it plays from the text, not memory.
- **Show my cards.** A toggle that adds your hidden cards and your open question to its table, so it can advise you. It's on its honour not to use them on its own turn.
- **Chat, Stop, settings.** Chat sent mid-run waits for the next run. Stop interrupts; Resume, or saying something, carries on. Model and Coach can change mid-game. Cost is shown as the API-equivalent.
- **Persistence.** Settings, chat, cost and the SDK session id are saved in `sessions/claude/<id>.json`, and a game resumes after a restart. Prompts are `prompts/game.md` and `prompts/coach.md`, read per run.
- **Later:** a takeback (replay minus your last decision) offered by the coach; filtering chain passes out of the move lines.

### Then

1. **Claude everywhere in the app.** With a Claude login, the chat is always there, not only in a game against Claude, and Claude can act in the app: open a scenario or session, start a game, move your view to a step, fork, set up a lesson, look up cards and decks. It's the same agent and chat panel as in a game, with a wider tool set.
   - **One tool layer, two ways in.** The tools are defined once, over the services the HTTP routes use (sessions, games, lessons, decks), with the same Zod schemas. The in-app agent gets them in-process (`createSdkMcpServer`, as the duel tools are now). The server also exposes them as an MCP server over Streamable HTTP (`/mcp`, local only), so Claude Code or another MCP client can drive the same app, and the browser follows along as it does for curl today.
   - **What the chat is attached to.** A conversation belongs to the app, not one session, and it's told what you're looking at (screen, session, step). In a game against Claude it stays the opponent: fair-play limits apply to its game tools, whatever else it can do.
   - **Alternative to weigh:** the browser-side WebMCP proposal (`navigator.modelContext`), where the page itself registers tools for an agent in the browser. It's still early; server-side MCP works today and covers Claude Code.
   - Subsumes "Claude drives the review" below, and gives lessons their tools.
2. **Lessons.** Claude sets up an opening hand and paces it with Next. It asks choice and text questions, and sets move prompts that it checks, undoing to show the right line if needed. It uses the existing lesson runtime (`server/lesson.ts`).
3. **Chat niceties.** Card names in Claude's messages open the inspector.
4. **Deck hub.** List decks, a Main/Extra grid with counts, import via decklist (with the 422 suggestions), edit and delete, per-deck sleeves, mat and deck box, plus "Teach me this deck" and "Play with this deck".

### Rules for games: OCG Core

EDOPro's `ygopro-core` has Lua scripts for almost every card and has been compiled to WebAssembly:
- [ocgcore-wasm](https://github.com/n1xx1/ocgcore-wasm) (MIT wrapper);
- [koishipro-core.js](https://github.com/purerosefallen/koishipro-core.js) (MIT wrapper, TypeScript, message parsing via `ygopro-msg-encode`).

**Spike result (2026-09-29): it works.**
- **Setup:** `koishipro-core.js` 1.5.5, which is MyCard's WASM build of the YGOPro core, updated September 2026. It uses the Fluorohydride `ygopro-scripts` and MyCard's `ygopro-database` `en-US/cards.cdb`. It runs in Node from CommonJS; its ESM WASM loader breaks under Node.
- **Test:** two random bots picking from the core's legal options played 50 seeded duels of the Chazz deck against itself.
- **Results:**
  - All 50 finished, averaging 19 turns, with zero script errors.
  - About 105ms per *whole duel*, so the engine adds no meaningful latency.
  - Every Chazz card name resolves to a card code, and 27 of 32 cards activated or were summoned. The other five need setups random bots rarely reach: VWXYZ, Armed Dragon Catapult Cannon, Ojama King, Ojama Knight, Triple Tactics Talent.
- **Fair play is built in:** each message has `playerView(player)`, which masks what that player can't see, and each prompt says who must answer it.
- **Answering prompts is simple:** every prompt type has a `prepareResponse(...)` builder. Invalid answers come back as `MSG_RETRY`.
- **Translation looks direct:**

  | Core message | Our action |
  | --- | --- |
  | `Move` | `move` |
  | `Draw` | `draw` |
  | `ShuffleDeck` | `shuffle` |
  | `LpUpdate` / `Damage` / `Recover` / `PayLpCost` | `lp` |
  | `NewPhase` | `phase` |
  | `NewTurn` | `nextTurn` |
  | `PosChange` | `position` / `flip` |
  | `ConfirmCards` | `reveal` |
  | `Chaining` / `ChainSolved` | `chainPush` / `chainResolve` |
  | `Summoning` etc. | step `intent` |

  The core names cards by controller + location + sequence. Field slots map one to one; in piles, copies are interchangeable, so a card leaving one is found by its code. ATK/DEF are read back with card queries and kept as modifiers. After every batch, tests check our board against the core's.
- **Licences:**
  - core: MIT;
  - scripts: GPL-2.0 (only matters if we distribute them);
  - the card database and `strings.conf`: no licence file, and the card text itself is Konami's.

  `npm run fetch-ocg` downloads the scripts, database and strings into `data/ocg/` (gitignored).

  These need care before hosting; they're fine locally.

**Games run on OCG Core** (see "Play against Claude" above). Free play, scenarios and lessons stay on our engine.

**Fallback (not planned): a Claude referee behind `RulesProvider`.**
- Instant checks in code (`basicRules`): one Normal Summon per turn, tribute counts, phase order, zone limits.
- Claude checks moves that matter (summons, activations, attacks, resolved chains) without blocking: the move applies, and the verdict arrives as a step warning with Undo.
- It uses a fast model with card text cached.
- The referee is a separate call from the opponent, because judging legality can need hidden information (your hand, what you searched). The opponent only sees verdicts.
- A real engine can replace it later behind the same seam.
